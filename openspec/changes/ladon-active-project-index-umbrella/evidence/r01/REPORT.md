# Active-index implementation, r01

The implementation adds source-change and exact-miss diagnostics, explicit lexical `index update`, and preview-first local index inventory/cleanup. The frozen [first-hand report](../../../../../FIRST-HAND-REPORT.md) is an input, not a file modified by this change. [Candidate hashes](candidate-hashes.json) identify the code and documentation bytes used for final verification; the base commit is recorded there. A [wheel-installed baseline](baseline.json) from that commit returned one lexical fallback for the untracked theorem in stored and verified modes, without an exact-miss summary; verified mode reported `stale-source`.

## Observed behavior

- [Portable CLI smoke](active-index-smoke.json): an untracked `Fresh.lean` produced `stale-source`, one added source and zero exact matches; after `index update`, the exact theorem was found. A subsequent edit appeared as one changed source. The updated search rows and generation identity matched a clean build. Prune reclaimed only the selected private index and left the default index hash unchanged.
- [Wheel-installed CLI smoke](installed-active-smoke.json): the same sequence passed on Python 3.11 and 3.12 using one wheel (`sha256:b229475a0e73a2533019f2f15a645dfc4f71c51a43f6a3735080c22b8bbb548b`). Both runs reclaimed the previewed 851,968 bytes and preserved the default index and a selected private index with retained binder evidence. The installed distribution smoke also passed its 29 contracts on each runtime.
- Portable regressions cover source add/edit/remove, excluded build paths, stable and unstable identity, exact counts before display limits, config/incompatible-base refusal, no-op, FTS/import parity, retained-evidence refusal, busy writer, source race, open reader, integrity/publication failure, lifecycle classification, replacement race, sidecars, partial deletion and persistent locks. The retained-evidence controls include diagnostic-only ProofIR, an unresolved v3 environment and a future prefixed table, each of which update and cleanup protect. Tests also retain the preregistered ranking source bytes unchanged.

## Cost and limits

The [final alternating benchmark](index-update-benchmark-final.json) uses a disposable 2,000-module, 20,000-declaration lexical population with one edited module per pair. Across five pairs, median update wall time was 0.566030 s and full build was 1.528598 s, a 62.97% reduction against the preselected 30% gate. All five pairs had equal generation identities. Update reused 1,999 modules and extracted one per pair. Reported process RSS was about 43.4–43.6 MiB for update versus 39.2–40.2 MiB for full build; sampled temporary directory peaks were about 60–79 MiB versus 56–74 MiB, including the retained private baseline index. These are shared-host, disposable-fixture observations, not a matrix-factorization performance claim. The benchmark records CPU, RSS, output hashes, final bytes and sampled disk peaks. The same frozen fixture also records a direct source-snapshot process (0.121 s, 91 output bytes), source-verifying status (0.243 s, 20,684 bytes), a name query (0.233 s, 16,318 bytes), and a private-index directory listing (0.122 s, 2,186 bytes), with their CPU/RSS observations. An earlier rerun stopped in the sampler when SQLite removed a journal between directory listing and `stat`; the sampler now skips vanished files. That incomplete run was not counted as a benchmark sample.

The implementation still hashes supported sources and copies the SQLite base. An update with retained semantic, lineage or ProofIR records refuses changed lexical publication with `full-build-required`; a no-change update preserves the existing generation. Cleanup protects ambiguous temporary and sidecar files rather than claiming their ownership. The reported 18 GB private-index population, 93-second historical query and August stale-configuration observation were not independently reproduced. Existing coverage, binder, lineage and ranking residuals remain with their linked OpenSpec owners.
