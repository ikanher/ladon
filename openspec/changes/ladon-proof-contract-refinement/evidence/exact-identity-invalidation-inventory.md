# Exact-identity invalidation inventory

Task 2.2 is accepted for the bounded set of outputs that actually depend on the rational refinement-branch type. The read-only dependency inspection is recorded on the canonical engineering board as finding #1095 and root acceptance #1096. The later rational ProofIR route supplies a branch-aware producer and checked-result artifact (see [native receipt consumer evidence](native-receipt-consumer-gap.md)); it does not make general source-context bridges or paired probes depend on refinement constraints. The dedicated stale-identity regression covers changed rule and base-goal inputs under unchanged human display identities and rejects reuse of old positive plan/cache evidence.

`create_refinement_branch` accepts bounded JSON expressions with a source span or proposed-repair rationale (`src/ladon/proof_contract_refinement.py`). Span and identity validation do not establish formula fidelity. The rational route now checks only the supplied finite assignment: it appends the cumulative predicates to a copied rational goal, lowers the resulting ground comparisons to Lean `Rat` obligations, and binds the branch, assignment, generated goals and replay receipts. This is an honest consumer of that closed rational meaning, but it does not establish a source-level term interpretation or a realization in an original mathematical context.

The generic consumers have different subjects. Contract-analysis probes regenerate obligations from contract and correspondence references plus a closed template (`src/ladon/_proof_contract_probe_native.py`); propagation replays its exact derivation, contracts and request (`src/ladon/proof_contract_payloads.py`); and the source-context bridge accepts a closed request containing repository root, correspondence reference, native context artifacts, deadline and limits (`src/ladon/proof_contract_context_bridge.py`). The context bridge reconstructs typed Lean obligations from the original application. None currently accepts a refinement branch or a mapping from rational AST variables to typed source-context terms.

Therefore adding a branch ID to one of those requests would not change the generated propositions and could falsely suggest branch-aware support. The rational assignment is ground, while a useful source-context adapter needs a checked realization or typed mapping that connects each branch predicate to the exact source/formal context. Re-running an existing consumer only rechecks its existing obligations. Until that semantic adapter exists, do not claim that generic bridge or paired-probe results are invalidated by changed refinement constraints.

This is an interface dependency boundary, not an impossibility result. The next sound extension is a bounded source-to-formal realization/constraint operation with exact typed bindings; until that capability exists, generic typed bridges and paired probes remain outside the branch-dependency claim. Do not broaden the current rational receipt route with metadata-only branch fields.
