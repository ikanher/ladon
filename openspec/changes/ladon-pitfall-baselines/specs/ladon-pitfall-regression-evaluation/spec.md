# Spec Delta

## Purpose

Frozen case populations, evidence-aware scoring, and matched pitfall development measurements. This capability retains exact evidence scope and explicit unresolved outcomes.

## ADDED Requirements

### Requirement: Fixed development population

The evaluator SHALL freeze 24 cases in six families, with two faults and two valid controls per family, actual pinned Lean counterparts, source text, expected evidence and stable case identities. Known article examples SHALL remain development inputs.

#### Scenario: Unsupported case

- **WHEN** one frozen case cannot be extracted
- **THEN** it remains in the denominator as unsupported and is not replaced by an easier example

#### Scenario: Counterexample substituted for the subject

- **WHEN** a row names a refutation certificate as the formal subject of its original claim
- **THEN** corpus acceptance fails until the original subject/comparison and validation certificate are bound separately

#### Scenario: Control proves less than its source promises

- **WHEN** a representation control only proves a bound, or a guarded-operation control omits the intended guard comparison
- **THEN** acceptance remains incomplete until the selected declaration establishes the promised behavior and its revised pairing is independently reviewed

#### Scenario: Matching hashes conceal a different source reading

- **WHEN** a comparison record assigns pointwise quantifiers to a quote claiming a uniform bound, even with matching span digests and declaration locators
- **THEN** corpus acceptance fails until the interpretation and obligation agree with the original source

#### Scenario: Expected evidence names a removed helper

- **WHEN** a case's evidence description requires a declaration that was removed or renamed during module isolation
- **THEN** the case remains unaccepted until the current evidence identity and its role are verified

### Requirement: Baseline custody

Baseline and enhanced arms SHALL bind exact local-checkout bytes, dependencies, toolchains, case files, invocation configuration, order and equal resource budgets. A dirty tree SHALL be represented by file digests rather than its commit alone.

#### Scenario: Installed package differs

- **WHEN** the pip-installed Ladon differs from the frozen checkout
- **THEN** the launcher uses the frozen checkout and records its actual runtime identity

#### Scenario: Compilation used a donor project

- **WHEN** a source file compiled using dependencies from a mutable external fixture
- **THEN** the receipt remains scoped to that execution and baseline custody requires preserved or reconstructable actual dependencies and a successful replay of the documented fixture entry point

#### Scenario: Imported artifact is stale

- **WHEN** a case source has changed but its imported compiled artifact has not been rebuilt or verified against that source
- **THEN** the import result cannot establish current-source qualification and the freeze gate remains incomplete

### Requirement: Staged family baseline unlock

Before the first family baseline or production semantic edit, the common corpus identities, judgment dimensions, command/tactic repertoire, preparation policy, ordering, scoring rubric and budgets SHALL be frozen. A child SHALL begin semantic runtime implementation only after independent acceptance of its complete family baseline and the shared evidence contract. Feasibility and provenance each require their four cases; operation-definedness requires all eight existence/defaults and operation-semantics cases. Each batch SHALL retain exact goal/evidence bindings, runtime reconstruction, freshness, live operational isolation, all outcomes and resource receipts. Versioned records with independent rubric-based adjudication SHALL suffice for this unlock; the full automated scorer SHALL remain mandatory for final acceptance.

Every baseline batch SHALL run the same preserved pre-change runtime and frozen policy, including batches measured after sibling implementation. Accepted first reports SHALL remain immutable. Final evaluation SHALL include all 24 original cases and validate the automated scorer against the reviewed family judgments. A changed policy SHALL identify a separate comparison rather than being mixed into the original results.

#### Scenario: Feasibility baseline is ready first

- **WHEN** all four feasibility cases have accepted baseline records, the common registration and shared evidence contract are accepted, and the full scorer and other families are pending
- **THEN** feasibility implementation may proceed while the other unlocks and full baseline remain incomplete

#### Scenario: Later batch accidentally uses enhanced code

- **WHEN** a remaining baseline batch invokes the developing checkout after a sibling changed the runtime
- **THEN** the batch is rejected as baseline evidence and must run on the preserved original runtime

#### Scenario: Later family harness remains unimplemented

- **WHEN** the common configuration registration, feasibility family baseline and shared evidence contract are accepted but a later family's harness is not yet qualified
- **THEN** feasibility work may proceed under its child controls, the later harness is qualified before its own batch runs, and its eventual commands and settings must match the registered configuration

#### Scenario: Original runtime lacks the diagnostic

- **WHEN** a registered capability probe with qualified invocation and subject/runtime bindings establishes that the original runtime does not support the requested diagnostic
- **THEN** independent adjudication may accept an unsupported baseline outcome without detection or justified-control credit, and the new semantic implementation remains work for the enhanced child

#### Scenario: Automated scoring disagrees with early adjudication

- **WHEN** the final scorer assigns a different judgment to an accepted family report
- **THEN** the disagreement remains explicit, corrections are appended, and final acceptance waits for independent reconciliation without rewriting the first report

### Requirement: Separate evaluation tracks

The evaluator SHALL score supplied-interpretation diagnostic capability separately from source-reading fidelity and any end-to-end discovery exercise. Supplied proof terms or selected fault annotations SHALL be disclosed and SHALL NOT count as autonomous detection.

#### Scenario: Oracle supplied a contradiction term

- **WHEN** a checker accepts a supplied witness of inconsistent assumptions
- **THEN** the case receives checker-validation credit but no unsupplied-search credit

#### Scenario: Imported helper exposes an answer

- **WHEN** an operational module or its dependency closure exposes a validation oracle, answer helper, label, or another case's answer certificate
- **THEN** operational readiness fails even if the oracle reference was omitted from the invocation JSON

#### Scenario: Proposition definition compiles

- **WHEN** Lean compiles a declaration defining a proposition without a proof of that proposition
- **THEN** scoring records statement elaboration only and does not award checked-proof or detection credit from compilation or the definition's axiom inventory

#### Scenario: Forbidden import fails for an unrelated reason

- **WHEN** a forbidden-import probe exits unsuccessfully because of a resource stop or unrelated compiler error
- **THEN** the result is not counted as verified module exclusion; isolation requires the expected resolution failure for that module and a successful positive control

#### Scenario: Probe environment expires before execution

- **WHEN** a temporary isolated import environment is destroyed before the operational command starts
- **THEN** its earlier probe cannot qualify that execution; the operational command must run under a live verified environment

### Requirement: Complete metrics

Reports SHALL retain every case, evidenced detections, false accusations, missed faults, justified controls, abstentions, extraction and checker failures, wall time, peak process-tree RSS and checker attempts. Aggregate coverage SHALL NOT erase per-family outcomes.

#### Scenario: Fast unknown results

- **WHEN** an arm returns unknown quickly for every case
- **THEN** its low runtime is reported alongside zero established detections, not as improved detection performance

### Requirement: Predeclared development gates

Each new semantic child SHALL establish both fault observations and justify both controls in its four-case supplied-interpretation family. The integrated development gate SHALL require zero false accusations, no lost baseline detections, and at least one newly established fault in each of feasibility, premise provenance and operation existence.

#### Scenario: All new cases pass but an existing control is accused

- **WHEN** the enhanced arm gains detections and falsely labels a valid domain transport
- **THEN** the integrated gate fails and the first report remains preserved

### Requirement: Independent scoring and compatibility

Case expectations and first reports SHALL be independently reviewed with corrections appended separately. The new evaluation profile SHALL leave the existing 24/12 contract-evaluation population and pending discovery gates unchanged.

#### Scenario: No independent adjudicator

- **WHEN** a run lacks independent classification review
- **THEN** results remain provisional and cannot close the integrated improvement gate


### Requirement: Qualified and reproducible operational invocation

The runner SHALL qualify its invocation separately from scoring, bind exact policy and runner bytes to the execution, and preserve actual arguments, source bytes, preparation and terminal attempt receipts. Effective tactics and resource settings SHALL agree with the frozen policy. The total case deadline SHALL include preparation and launcher setup, and expiry SHALL stop the process tree and retain a resource outcome. RSS and virtual-address-space limits SHALL NOT be treated as interchangeable.

#### Scenario: Correct invocation exposes an original-runtime limitation

- **WHEN** custody, isolation and invocation qualification pass but capture or replay is unsupported or fails in the original runtime
- **THEN** the case retains an unresolved outcome and the remaining cases execute; independent baseline acceptance does not require repairing that runtime

#### Scenario: Harness qualification fails

- **WHEN** the invocation, input binding or isolation cannot be qualified
- **THEN** execution remains an unscored qualification trial and cannot unlock a child or contribute a mathematical abstention to accepted metrics

#### Scenario: Registration leaves a query unspecified

- **WHEN** a profile lacks the exact proposition query, source position or goal selection needed for its actual subject
- **THEN** the family cannot run under that profile until a separately identified correction binds and independently reviews those inputs; choosing them inside the runner does not qualify the original registration

#### Scenario: Query targets a definition or theorem

- **WHEN** a generated query represents a proposition-valued definition or a theorem declaration
- **THEN** its goal is bound respectively to the definition's proposition value or the theorem's fully quantified proposition type, preserving original dependent binders and premises; neither the sort `Prop` nor a theorem proof constant substitutes for the intended proposition

#### Scenario: Wrong preserved toolchain selected

- **WHEN** the selected Lean/Lake executables or imported artifacts do not match the case's frozen fixture toolchain
- **THEN** qualification fails before scoring; a successful control in another toolchain cannot establish readiness for this fixture

#### Scenario: Corrected profile attempts both polarities

- **WHEN** a successor profile attempts the original proposition and its negation
- **THEN** the reviewed profile binds both queries and their ordering, shares the original case budget across preparation and attempts, retains failed search as unresolved, and requires checked evidence for either conclusion

#### Scenario: Successor registration reuses accepted families

- **WHEN** a corrected query protocol changes only pending families and reuses earlier accepted family records
- **THEN** those records retain their original registration identities with reviewed unchanged-profile compatibility, and matched enhanced evaluation uses the same corrected protocol for each affected family

#### Scenario: Injected module fails for an unrelated reason

- **WHEN** the deliberately exposed module fails to import because of a resource stop or unrelated compiler error
- **THEN** the availability control is unqualified; it must import successfully before its rejection by the exclusion predicate demonstrates the guard

#### Scenario: A later polarity replaces the probe file

- **WHEN** preparation reuses a source path for a later attempt
- **THEN** the prior attempt retains immutable source bytes and invocation receipts matching its capture digest

#### Scenario: Policy settings differ from executed settings

- **WHEN** executed tactics, bounds or runner identity differ from the frozen registration
- **THEN** the run cannot be accepted under that registration, even if its policy name and runtime identity still match

#### Scenario: Shared deadline expires

- **WHEN** preparation, setup and attempts exhaust the case deadline
- **THEN** execution terminates the case process tree and retains preparation, completed and interrupted attempt receipts without resetting the budget or losing the case record


#### Scenario: Successful capture has an invalid source binding

- **WHEN** a report claims successful capture but its required source binding is missing or differs from the attempted source
- **THEN** the runner retains an unscored qualification failure rather than a mathematical abstention, and does not continue scored execution
