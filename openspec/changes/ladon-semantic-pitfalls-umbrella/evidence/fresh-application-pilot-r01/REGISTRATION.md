# Fresh checked-application workflow diagnostic r01

Registered before any auditor launch. Two short, constructed source/Lean units ask whether a proposed Mathlib theorem supports an attributed passage. The first passage must be read before exposing the formal candidate. Each unit is delivered separately to a fresh agent with no conversation history or reference answer. The input hashes are in INPUTS.json. The local dependency cache is retained from the previous synthetic project; the Mathlib and Lean toolchain are pinned at Lean 4.33.0. The source owner `Nat.sInf_mem` is compiled Mathlib. `Owner.lean` defines the proposition without proving it; `Query.lean` is an incomplete goal wrapper for native capture, not a certificate. The donor repository is not accessed.

Prediction: source-context application checking may reduce false reassurance about a missing premise while preserving support when that premise is derivable. Compare the same Luna-6-medium auditor, same source and general audit recipe, same ordinary Lean access and time budget. The assisted arm additionally receives the Ladon checkout commands and may use native capture/completion. No selected obligation, diagnosis, counterexample or oracle is disclosed. Each unit gets one control and one assisted report, four separate contexts. Assignment order is A-control, B-assisted, A-assisted, B-control as capacity allows; agents cannot inspect the other unit, runs, custody or prior studies.

Each arm has 15 minutes from dispatch, at most 20 top-level checking commands, 12 GiB RSS and 16 MiB output for substantial Lean/Ladon operations, 600 seconds maximum per operation and the stricter remaining arm deadline. Agents record first source-only interpretation before theorem inspection, checking attempts, final verdict and unresolved scope. A final report can state support, discrepancy, or unresolved; bare proof-search failure is not a refutation. Auditor reports are frozen before custody/answer inspection. Root performs informed mathematical adjudication afterward; no treatment-blind or independent review is claimed. No comparative superiority or general accuracy conclusion can be drawn from two designed units.

Primary descriptive endpoint: on each unit, did the arm give correct, source-justified support/discrepancy/abstention without false reassurance or a false accusation? Secondary: exact checked application or countermodel, native replay/trust, command failures, wall time and unavailable costs. The comparison tests a mechanism, not a numerical gate. Distinguish tool access from actual native use and preparation time from auditor time. Both arms have the same proposition definitions and local Mathlib cache; native source-goal wrappers are available to both. Preserve first reports and command receipts. Original known N.3 cases and earlier evaluation outcomes are excluded from auditor input.
