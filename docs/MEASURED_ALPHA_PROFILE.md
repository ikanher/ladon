The registered [r34 discovery study](../openspec/changes/ladon-authority-safe-verified-discovery-umbrella/evaluation/discovery-execution-r34.json)
uses four portable cases, two matrix-factorization calibration goals, and two
held-out repository families. The four portable cases recovered every labeled
candidate and replayed scratch successfully. Matrix native `exact?` and `apply?`
closed both calibration goals without `sorryAx`; their largest sampled process
group used about 8.43 GiB, within the 32 GiB bound. Ladon encountered a Real
notation checker failure and source-population drift. The standalone mathlib
environment lacked compiled dependencies, and the dp-clipping toolchain was
unavailable. These are incomplete external outcomes, not baseline wins or
incorrect-suggestion judgments. Shared-host timing is not a controlled speed
comparison, and label recall does not assess every possible correct proof.

A post-study regression on `Mathlib.Data.Real.Basic`, with local
`epsilon:Real`, goal `epsilon = epsilon`, and candidate `Eq.refl`, succeeded on
both installed r37 runtimes. Publication and advisory scratch compilation
passed, with about 3.38 GiB peak sampled memory. This explicit-candidate check
does not exercise freshness-verified shortlisting or establish held-out
performance. The much larger matrix module imports 10,511 modules and exceeds
the r37 reader's 10,000-module evidence cap. It remains unsupported by that
historical candidate. A later capacity follow-up supports up to 32,768 compiled
modules and captures the fixed-epoch polynomial application with 10,517 modules
on both installed Python runtimes. See the
[field follow-up](../openspec/changes/ladon-result-understanding-and-release-umbrella/field-feedback-matrix-fixed-epoch.md#canonical-capacity-fix-r42)
for its separate development evidence and remaining source-anchor gap. This
does not change the r37 study population or its readiness classification.
